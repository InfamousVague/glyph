The relay is mostly two WebSockets, the hub and the pairing relay. Beside them it answers a small set of plain HTTP routes: a circle's sealed files, the plugin Marketplace, feedback, and the pages that link a handle. This page lists every one. The public relay is at https://gogho.st. Anyone can run their own from the source: dart run relay/bin/relay.dart --port 8787. The WebSocket protocols are on The hub and pairing protocols, and a Postman collection of these routes is on API overview and Postman.

Conventions

  • No CORS. The relay sets no Access-Control-* header and has no OPTIONS handling. These routes are for the app and for scripts, not for a page in a browser on another site.
  • No match is not an error. A request that fits no route, whatever its method, answers 200 with the plain text Ghost Messaging relay. There is no separate health route: this is it.
  • JSON answers are application/json; charset=utf-8. Request bodies are read as UTF-8 JSON or raw bytes; no Content-Type is looked at.
  • Hex is lowercase. Ids and hashes in paths must match their shape exactly, or the route does not exist.
  • Times are whole milliseconds since 1970, as decimal digits.
  • Per-address limits go by the first value of X-Forwarded-For, or the connection's address where there is none.

Each module says no in its own shape:

ModuleA refusalNotes
Files{"err": "No such space."}A sentence. A few carry more: have, done, seq.
Feedback{"error": "Feedback is sent with POST."}A sentence, under error, not err.
Marketplace{"ok": false, "error": "not_found", "message": "There's nothing here by that name."}error is a fixed code; message is for people. Every success carries "ok": true.

Outside the modules, a path whose percent-escapes are not UTF-8 answers 400 with no body, and an error nothing else caught answers 500 with no body.

Signing a request

Writes to Files, feedback, and most of the Marketplace are signed with the install's own key, the same one the hub knows it by. No account or password is involved.

ThingFormat
KeyP-256 (secp256r1). The public key is 33 bytes compressed: 02 or 03, then x. In a header it is standard base64 with padding, 44 characters.
SignatureECDSA over the SHA-256 of the signed string. 64 bytes: r (32, big-endian) then s (32). Not DER. Standard base64, 88 characters.
IdThe first 16 bytes of the SHA-256 of the 33 key bytes, as 32 lowercase hex digits. This is who the relay says wrote something.
Body hashSHA-256 of the body's bytes, 64 lowercase hex digits. For an empty body: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855.

All three modules take the same three headers and sign five lines joined by a line feed (\n), as UTF-8, with no line feed after the last. Only the first line and a few rules differ.

x-ghost-key:  <base64 of the 33-byte public key>
x-ghost-time: <milliseconds since 1970>
x-ghost-sig:  <base64 of the 64-byte signature>

The relay remembers what each key signed, so the same request sent twice is refused the second time. To try again, sign again with a new time.

Files

Every Files route but GET /files also carries the space's token: Authorization: Ghost <token>, 64 lowercase hex digits. Reads need only the token. Writes need the token and the signature.

ghost-files v1
<METHOD>
<path and query, as sent>
<time>
<body sha256 hex>
  • The third line is the whole request target, query included: /files/0123456789abcdef0123456789abcdef/log?after=7.
  • The time may be up to 10 minutes from the relay's clock, either way.
  • Where the body is not read (DELETE /files/{space}, POST …/done), sign the empty body's hash.
  • For a blob's piece sent with x-ghost-body-sha256, the last line is that header's value, and the signature is checked before the body is read.
  • Any failure answers 401 {"err": "Bad signature."}.

Marketplace

ghost-market v1
<METHOD>
<path>
<time>
<body sha256 hex>
  • The third line is the path alone. A signed request with any query string is refused.
  • The time may be up to 5 minutes from the relay's clock.
  • A POST must say its body up front, in two more headers: x-ghost-body-sha256 (64 lowercase hex digits; the last signed line) and x-ghost-body-length (the length in bytes, equal to Content-Length). A chunked body is refused.
  • A GET or DELETE must send neither of those headers and no body, and signs the empty body's hash.
  • A missing header answers 401 unsigned. A bad key, time or signature, or a repeat, answers 401 bad_signature. A broken shape (a query, a header sent twice, a length that does not match) answers 400 bad_request.

x-ghost-time: 1795000000000
x-ghost-sig: <88 base64 characters>

Signatures inside Marketplace bodies

Review's decisions are signed a second time, by the reviewer's key, so that the apps can check them without trusting the relay. Each is the same kind of signature over lines joined by \n, and travels as a JSON object with exactly the fields shown. Here key and sig are strict base64: the standard alphabet, padded, no whitespace.

WhatSigned stringObject
Approvalghost-market approve v1\n<plugin>\n<version>\n<sha256>{"v": 1, "plugin", "version", "sha256", "key", "sig", "at"}
Revocationghost-market revoke v1\n<plugin>\n<sha256>\n<at>\n<why>{"v": 1, "plugin", "sha256", "at", "why", "key", "sig"}
Retirementghost-market retire v1\n<key> (the key's base64 text){"v": 1, "key", "at", "sig"}

General

The relay has one answer for anything it does not recognise. A script can use it to see that a relay is there.

Sign-in links

These are pages for a browser, not an API to call. When someone links a Discord, Telegram or X handle, the app asks the hub for a sign-in address and opens it. The address holds a state made for that install, good for 10 minutes and for one sign-in. The relay checks the sign-in with the network, links the handle, and tells the install over the hub. A network whose keys are not set on the server is off, and its page says the link is no good.

Invite words

A circle can be joined by a word. The relay keeps, under the SHA-256 of the word, a sealed link of at most 1024 characters that the app gave it over the hub. It never sees the word or what the link opens. This one route is how the site's join page looks a word up.

Files

A space's files live on the relay as sealed blobs, beside an ordered log of sealed operations that says what the files are. The relay can't read either: names, keys and contents are sealed by the apps. It sees the space's id, each blob's size, when things were written, and the id of the install that wrote them.

A space is named by an id (32 hex digits) and guarded by a token (64 hex digits), both made by the apps from the space's secret. The relay keeps only the token's hash, and a wrong token is answered exactly as a space that isn't there. Anyone with the token can read. Writing also takes a signature, so a blob is written and finished only by whoever started it, and removed by them, the space's owner, or a moderator who shows the space's signed roster.

Uploading a file is three steps: reserve a blob with its size, send its pieces in order, then finish it. An upload cut short carries on from have.

Feedback

The app's Share feedback sends one signed report. The relay files it on the server's feedback board and answers with the ticket's id. It keeps nothing itself. A username in the report is filed as given when the signing key holds that username, and marked not verified otherwise. On a relay with no board set up the route answers 503.

Limits: 5 reports an hour and 20 a day from one install, 300 a day from everyone, 10 MiB a report, three screenshots of 3 MiB each.

Marketplace

The Marketplace holds plugins from other developers and the queue they wait in for review. A plugin's package is one JSON file in the ghost-plugin/1 format, sent in canonical form (keys sorted, no whitespace) and named by its SHA-256.

Anyone can read the catalog, the withdrawals list, approved packages and listed screenshots. A developer signs with the key that holds the username in the plugin's developer field. Review is an install that holds one of the relay's admin usernames and signed in to the admin page over the hub in the last 8 hours, or the last 30 minutes for approving, revoking, blocking and listing. No password travels over these routes.

The relay is not trusted with a plugin. An approval is the reviewer's own signature over the plugin's id, version and hash, and the app checks it against review keys it already knows before it adds anything. The catalog carries no names or pictures: the app fetches each package and reads them from it.

The relay keeps packages, screenshots, submissions with their notes, reports, and a log of what review did. A report is kept without its sender's key.

POST /market/submissions with {"check": true, "package": "…"} runs the relay's checks and keeps nothing. Submit a plugin covers the app's side.

Running your own

The relay is one Dart program with no dependencies beyond Dart's own library. It listens over plain HTTP on this machine alone unless told otherwise, so on a server it sits behind a web server that holds the certificate.

dart run relay/bin/relay.dart [--host 127.0.0.1] [--port 8787] [--data relay-data] [--verbose]
FlagDefaultMeaning
--host <address>127.0.0.1Where to listen.
--port <number>$PORT, else 8787The port.
--data <folder>relay-dataWhere everything it keeps is written.
--verboseoffSays when an install joins or leaves. Never an address, never a whole id.
--help, -hPrints the flags.

Everything else is set in the environment. Each family is optional: a feature whose values are not set is off, and every limit has a default.

Your own relay can run a Marketplace, but the app adds a plugin only when its approval is signed by a review key the app was built with. Approvals from your relay's reviewers mean nothing to an unchanged app.

The full list of variables, with each one's least and most, is in the source: relay/lib/files.dart, relay/lib/market.dart, relay/lib/handles.dart, relay/lib/feedback.dart and relay/lib/pushes.dart.
