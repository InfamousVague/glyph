The hub and pairing protocols

What an app says to the relay server over a WebSocket: signing in, packets, presence, rooms and the directory.

The relay server speaks two WebSocket protocols. The hub is where installs find each other: any address ending in /hub, so wss://gogho.st/hub. A pairing channel joins one phone to one of its computers: an address ending in 32 hex digits, wss://gogho.st/relay/<channel>. Both pass sealed bytes the server can't read. Its plain HTTP routes are in the relay's HTTP routes, and how the app uses all of this is in Routes.

On both, a text frame is one JSON object and a binary frame is a sealed packet. The server pings each socket every 30 seconds. The code is relay/lib/hub.dart and relay/lib/relay.dart; the app's side of the hub is lib/net/hub_carrier.dart.

Who an install is

An install is a P-256 (secp256r1) key pair made on the device. The hub knows it by a name made from the public key. There is no account to make first: anyone with a key can sign in.

ThingWhat it is
Public key33 bytes, compressed: 02 or 03, then x. Sent as base64 in the sign-in, whois and acct-put; as 66 lowercase hex digits for a read-only room's owner.
Name (id)The first 16 bytes of SHA-256 of those 33 bytes, as 32 lowercase hex digits. In binary frames it is the 16 raw bytes.
SignatureECDSA over SHA-256 of the message, as 64 raw bytes: r, then s, big-endian. Not DER. Sent as base64 in the sign-in and in bind; as 128 lowercase hex digits in a read-only room's grants.
Account addressA Ghost account is a second key, secp256k1, known by an Ethereum-style address: 0x and 40 hex digits. Only the account messages use it.

All hex the server reads is lowercase.

Signing in to the hub

  1. Open a WebSocket to wss://gogho.st/hub. With 20,000 sockets open already, the upgrade is refused with HTTP 503.
  2. The hub speaks first, with a number made for this connection (32 random bytes, as 64 hex digits): 
    {"hello": "<64 hex>", "peek": true, "react": true}
    peek says this hub knows the look-only sign-in below. react says it takes reaction packets.
  3. Within 10 seconds, answer with one text frame: 
    {"id": "<32 hex>", "key": "<base64, 33 bytes>", "sig": "<base64, 64 bytes>", "device": "desk-1"}
  4. The hub answers, then hands over what it held for you as binary frames: 
    {"ok": true, "held": 3}
FieldWhat it holds
idYour name. It must be the one made from key.
keyYour public key, base64.
sigYour signature, base64, over the 13 bytes of ghost-hub v1 (with its space) followed by the 32 raw bytes of the hub's number: the hex decoded, not the hex text.
deviceOptional. Which of your devices this is, 64 characters at most. Left out, too long or not a string, it counts as the empty string.
peekOptional. true makes this a look only.

One name can be signed in from 8 devices at once. A new connection with the same device takes the older one's place, and a ninth device takes the place of the one connected longest. The connection that lost its place is closed with 4409.

A look

With "peek": true the hub says how much is waiting and closes the socket with 1000 (looked). Nothing is handed over or removed, and no other connection of yours is replaced. A closed app uses it to see whether it should wake.

{"ok": true, "held": 3, "peek": true, "here": false}

here says whether any device of this name is connected now.

Refusals and close codes

After signing in

A text frame is known by its keys, tried in this order: ping, push, dir, watch, away, join, anchor, leave, look, unlook. The first that matches decides. {"ping": 1} is answered {"pong": 1}, with whatever value was sent.

No answer means ignored

A frame that isn't a JSON object, a dir the server doesn't know, an unknown first byte and a binary frame too short for its kind all get no answer. A client can't tell ignored from lost.

Packets to a person

A binary frame's first byte is its kind. Kind 0x01 is a packet to one name. The payload is sealed by the apps; the hub doesn't read it. The hub puts the sender's name in itself, so nobody can send under another's.

DirectionBytesHolds
To the hub00x01
1 to 4seq: a number you choose, uint32, big-endian. It comes back in the answer.
5 to 20The recipient's name, 16 bytes.
21 onThe payload, one byte at least.
From the hub00x01
1 to 16The sender's name, 16 bytes.
17 onThe payload.

A whole frame is 65,568 bytes at most (64 KiB and 32 bytes for headers). A longer one, or an empty one, closes the connection with 1009.

The packet goes to every connected device of the recipient except the connection that sent it. Each one is answered with a text frame:

AnswerMeaning
{"ack": <seq>, "here": true}Passed to at least one connected device.
{"ack": <seq>, "here": false}Nobody was there. It is held, and a push is asked for where the recipient registered one.
{"nak": <seq>, "err": "full"}Nobody was there and it could not be held.

Held for someone away

The hub holds up to 200 frames and 1 MiB for one name, 96 MiB for everyone together, for 7 days. When the name next signs in, its mailbox is emptied and everything not too old is handed over, right after {"ok": true, "held": n}. An ack means the hub took the packet, not that the other app opened it.

Held in memory

Held packets are kept in memory only. A restart of the server loses them.

Presence

A connection asks about names with watch, and from then on is told when they come and go. Watches add up for the life of the connection, to 500 names. There is no message to stop watching.

{"watch": ["<id>", "<id>"]}

Answered at once, about the names in that message:

{"here": ["<id>"], "away": ["<id>"], "seen": {"<id>": 1763900000000}}
FieldMeaning
hereNames connected now.
awayNames connected with every device put away.
seenFor names not connected, when each was last here, in milliseconds since 1970. The hub remembers this for 200,000 names.
MessageFromMeaning
{"away": true} or falseYouThis device was put away, or is back in use. Not answered.
{"came": "<id>"}HubThe name's first device connected.
{"went": "<id>", "at": <ms>}HubIts last device disconnected. at is when it was put away, if it had been, else now.
{"away": "<id>", "is": <bool>, "at": <ms>}HubWhether all of its devices are away has changed.

Rooms

A room is how more than two installs talk, such as a space or a circle's channel. Its name is 32 hex digits and its token 64 hex digits, both made by the apps. The first to join sets the token; the hub keeps only its SHA-256. A room with nobody in it is forgotten, though the packets it kept are not.

{"join": "<32 hex>", "token": "<64 hex>"}
AnswerWhen
{"room": "<room>", "ok": true, "members": ["<id>"]}Joined. members is the other names in it, not yours. In a read-only room there is also "ro": "writer" or "ro": "reader". The room's kept packets follow as binary frames.
{"room": …, "ok": false, "err": "bad room"}The name isn't 32 hex digits or the token isn't 64.
{"room": …, "ok": false, "err": "bad anchor"}A read-only join whose name isn't made from its base and owner.
{"room": …, "ok": false, "err": "refused"}The wrong token, or this connection is in the other room of that name (ordinary or read-only).
{"room": …, "ok": false, "err": "full"}The room has 64 names and yours isn't one, or the hub has 50,000 rooms and this would be a new one.

Every device of a name can be in a room. The room counts names, not devices.

MessageFromMeaning
{"room": "<room>", "came": "<id>"}HubA name's first device joined. Sent to everyone else in the room.
{"room": "<room>", "went": "<id>"}HubA name's last device left or disconnected.
{"leave": "<room>"}YouLeaves the room. Not answered.
{"look": "<room>", "token": "<64 hex>"}YouAsks who is in an ordinary room without joining it. 200 looks a connection at most.
{"room": "<room>", "look": ["<id>"]}HubWho is in the room now, sent at once and again whenever that changes. An empty list for a room that doesn't exist. With the wrong token, nothing is said, now or later.
{"unlook": "<room>"}YouStops the looking. Not answered.
{"anchor": "<room>", "gv": …, "g": {…}, "gs": "…"}YouHands a read-only room you are in a newer list of admins. Not answered.
{"room": "<room>", "ro": "refused"}HubA reader in a read-only room sent a kept packet. It was neither kept nor passed on.

Room frames

DirectionBytesHolds
To the hub00x02 a packet, 0x03 a packet to keep, 0x04 a reaction.
1 to 16The room's name, 16 bytes.
17 onThe payload, one byte at least. A reaction's is 512 bytes at most.
From the hub00x02 for a packet, kept or not; 0x04 for a reaction.
1 to 16The room's name.
17 to 32The sender's name, 16 bytes.
33 onThe payload.
KindWhat the hub does
0x02Passes it to every other connection in the room, the sender's other devices too. Not answered. Ignored from someone not in the room.
0x03As 0x02, and keeps it for whoever joins later. It arrives as 0x02.
0x04Keeps it and passes it to everyone else in the room, readers too. One over 512 bytes is dropped without a word.

A room keeps its newest 300 frames for 7 days, within 256 MiB over all rooms. A device that joins with the token they were kept under is handed them, in order, after the answer to its join.

Older hubs

A hub that doesn't say "react": true in its hello doesn't know kind 0x04. The app sends a reaction to one as a kept packet instead.

Read-only rooms

In a read-only room only the owner and the admins the owner named may post. Its name is tied to the owner's key, so nobody else can open it first. Join with an ro object:

{"join": "<room>", "token": "<token>",
 "ro": {"base": "<32 hex>", "owner": "<66 hex>", "gv": 2,
        "g": {"<admin id>": "<128 hex>"}, "gs": "<128 hex>"}}
FieldWhat it holds
base16 bytes the app chose, as hex.
ownerThe owner's public key, 33 bytes as hex. The room's name must be the first 16 bytes of SHA-256 of ghost-ro|, then the 16 bytes of base, then the 33 bytes of owner.
gThe admins: each name with the owner's signature over ghost-circle admin|<owner hex>|<id>. 200 entries at most. An entry whose signature is wrong doesn't count.
gvOptional. The list's generation, a whole number. A list with a higher one replaces the one the room has.
gsNeeded when gv is above 0: the owner's signature over ghost-circle grants|<owner hex>|<gv>|<g as JSON>, with g's keys sorted and no spaces.

The owner's own name always may post. A reader's 0x03 is refused, a reader's 0x02 reaches the writers only, and a reader's 0x04 reaches everyone. A read-only room is kept apart from an ordinary room of the same name, and a connection can be in one of the two at a time. anchor takes the same gv, g and gs later on.

Pushes

An iPhone's app tells the hub its Apple push token, so that it can be woken when a packet is held for it. Android phones look for themselves, with a look.

MessageEffectAnswer
{"push": {"apns": "<hex>", "sandbox": false}}Keeps the token for this name. apns is 32 to 200 hex digits. sandbox counts only as true.{"push": true}, or false from a server that sends no pushes.
{"push": null}Forgets the token. So does any value that isn't such an object.The same.

The notification says only Ghost Messaging and New message, once a minute for one name at most. The server never has the words of a message to put in it.

The directory

Messages with a dir key ask the server's directory: usernames, linked handles, badges, accounts and invitations. Each is {"dir": "<name>", …} and its answer comes back on the same connection as another dir message. They aren't numbered: match an answer by its dir and the fields it repeats.

A refusal looks the same for all of them. err is a sentence to show the person:

{"dir": "err", "about": "claim", "err": "A username is 3 to 20 letters, numbers, dots or underscores."}

The messages under Usernames, Linked handles, Number verification and Badges also repeat the p that was sent. Something unexpected is answered That did not work. Try again in a while. A server run without one of these parts answers This server keeps no accounts. (or no invite words, no invites, no handles).

Two hashes appear throughout, both SHA-256 as 64 hex digits. A username's key is the hash of ghost-name v1|<username>. A handle's key k is the hash of ghost-handle v1|<network>|<handle>. Both are tidied first: trimmed, lower case, no leading @, and a phone number in E.164 form.

Usernames and profile

A username is 3 to 20 characters from a-z, 0-9, . and _, starting with a letter or digit, with no two dots together. Some words are reserved (admin, support, ghost and the like). An install holds one at a time.

Accounts

A Ghost account is an address holding two sealed backups of one identity: one sealed by the password, one by the recovery words. The server can open neither. Four of these messages must be signed by the account's key, and come in an envelope:

{"dir": "acct-put", "body": "{\"op\":\"put\",\"a\":\"0x…\",\"by\":\"<your id>\",\"at\":1763900000000,…}", "sig": "<130 hex>"}
  • body is a JSON object written as a string, 196,608 characters at most. It always holds op (put, seed, devices or delete), a (the address), by (the name of the connection saying it) and at (the time in milliseconds, within 10 minutes of the server's clock).
  • sig is a secp256k1 signature over the EIP-191 personal-message hash of body's bytes exactly as sent: keccak256 of \x19Ethereum Signed Message:\n, the byte length in decimal, then the body. 65 bytes (r, s, v) as hex, 0x optional, v as 27 or 28 or as 0 or 1, low s only. The address it recovers to must be a.
  • Each body is taken once. Saying it again is refused.

One account for an identity, and one identity for an account.
acct-findname: a username.{"dir": "acct-find", "name", "phone", "kdf"}: whether a texted code is needed, and the settings to stretch the password with (v, k, m, t, p, s). No account: {"dir": "acct-find", "name", "none": true}. 30 an hour.
acct-textname; number: the account's verified number.{"dir": "acct-text", "name", "sent": true}. Only the right number is texted. 5 wrong numbers an hour.
acct-getname; auth: the password proof, 32 bytes as hex; number and code where the account has a verified number.{"dir": "acct-get", "name", "a", "blob"}: the address and the password-sealed backup. acct-seed (signed)Nothing more.{"dir": "acct-seed", "a", "blob", "pw"}: both backups, for someone who signed in with the recovery words. No account: {"dir": "acct-seed", "a", "none": true}.

The password itself never reaches the server. The app stretches it with Argon2id, sends a proof made from the result as auth, and the server checks only that the proof's SHA-256 is the pwv it was given. Signed changes are held to 60 an hour for a connection's name.

Invitations

An invitation waits for someone who isn't on the app yet, under a hash of their number: h is the handle key of that number on the network phone. b is the invitation, sealed by the app, as base64 of 2,048 characters at most.

MessageTakesAnswer

invitesh{"dir": "invites", "h", "list"}: each as {"i", "b", "at"}. Only for the install that verified that number by text.
invites-droph; ids: a list of i.{"dir": "invites-drop", "left"}: how many still wait.

A number has 20 waiting at most, 3 of them from one sender, and each waits 30 days.

Invite words

A circle's invite word stands for its invite link. The word is never sent: h is its SHA-256 as 64 hex digits, and b is the link sealed by the app, 1,024 characters at most.

MessageTakesAnswer

word-droph{"dir": "word-drop", "h", "ok": true}, also when there was no such word. Refused for someone else's.

A word not set again within 365 days is let go. The same lookup is there over HTTP, as GET /word/<h>.

Pairing channels

A channel passes frames between a phone and one paired computer. Its name is the last part of the address: 32 lowercase hex digits. No headers or query are read. A WebSocket to any other address that doesn't end in hub is answered 404.

The first frame, within 10 seconds, says the channel's token and which end this is:

{"auth": "<64 hex>", "role": "phone"}
FieldWhat it holds
authThe channel's token. The first connection to a channel sets it, and the relay keeps only its SHA-256. Later ones must say the same.
rolephone or desk. One socket for each; a newer one in the same role replaces the older.
tempOptional. true, on the hello that makes the channel, makes it a temporary one, made for pairing.

After that:

MessageFromMeaning
{"ok": true, "peer": <bool>}RelayYou are in. peer says whether the other end is connected now.
{"ok": false, "err": "bad hello"}RelayThe hello wasn't JSON text, or its auth or role was wrong. Closed with 4400.
{"ok": false, "err": "refused"}RelayNot this channel's token, or the relay has all the channels it keeps. Closed with 4403.
{"peer": true}RelayThe other end joined.
{"peer": false}RelayThe other end's socket closed.
A binary frameEither endPassed to the other end as it came, 1,048,640 bytes at most (1 MiB and 64 bytes).
{"dropped": true}RelayYour binary frame went nowhere: the other end isn't connected.
{"delete": true}YouUnpairs. The channel is removed and both ends closed with 4410.
{"ping": <value>}YouAnswered {"pong": <value>}.

Any other text frame is ignored.

What is kept

No frame is kept or queued. With the other end away a frame is dropped and its sender told. Of a channel the relay keeps its name, the hash of its token and the day it was last joined, and forgets it 90 days after that day when nobody is connected. A temporary channel is never written down. It lasts 10 minutes, or until both ends have left if that is sooner.
